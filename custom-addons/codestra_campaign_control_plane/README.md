# Codestra Campaign Control Plane

This addon owns the Odoo-side campaign control plane on the canonical
`cc.campaign` record: application registries, immutable template versions,
typed profile fields, workspace layout metadata, integration bindings,
immutable campaign configuration versions, the campaign control lifecycle,
provisioning runs, and actual-state read-back receipts.

It does not provision providers or call external systems directly, and it
does not own a provisioning manifest: per the locked design specification
(`docs/superpowers/specs/2026-09-15-odoo-unified-campaign-control-plane-design.md`,
section 8.3), Middleware alone owns the canonical provisioning manifest.
`cc.campaign.configuration.version` records only the Odoo desired
configuration snapshot/hash; the contract's `manifest_ref` / `manifest_hash`
are Odoo's reference to that version
(`odoo://cc.campaign/{workspace_uuid}/configuration-versions/{n}` and
`sha256:{configuration_hash}`).

## Shared contract

Every Middleware-facing operation is pinned by
`contracts/odoo/campaign-control.v1.json` (vendored byte-identical from the
Middleware repository; canonical SHA-256
`874711f3a8c38bfb2c69169d5f7c1717897d48419ce60bf5649a899f023e1e03`, the value
Middleware migration 0066 pins). `tests/test_shared_contract_parity.py`
proves the hash, route/method/scope parity, request-schema parity, the
effective-state and outbox-event vocabularies, capabilities and the YAML
catalog (`call_center_campaign/docs/ODOO-ENDPOINT-CATALOG.yaml`, generated by
`scripts/generate_odoo_endpoint_catalog.py`).

| Operation | Route | Scope |
| --- | --- | --- |
| `campaign.actual_state.write` | `POST /api/v1/integration/campaigns/actual-state` | `odoo.campaign.actual_state.write` |
| `campaigns.read` | `POST /api/v1/integration/campaigns/read` | `odoo.campaign.control.read` |
| `desired_state.read` | `POST /api/v1/integration/desired-state/read` | `odoo.campaign.control.read` |

`odoo.campaign.control.write` is held only by the separately authorized
administrative platform client on `/platform/v1/campaigns*`; Middleware never
receives it. `/api/v1/integration/campaign-actions` is retired: it answers
`410 Gone` and is not advertised.

## Vocabulary

* `desired_state` and `effective_state` use only the contract enum
  `unknown`, `absent`, `provisioned_disabled`, `synthetic_tested`, `active`,
  `disabled`.
* `control_status` (`draft`, `validated`, `blocked`) is Odoo configuration
  progress and is reported as `lifecycle_status`; it is never an effective
  state.
* `cc.campaign.provisioning.run.status` is `pending`, `succeeded` or
  `failed`; its outbox `delivery_state` (`queued`, `accepted`, `dead_letter`)
  is separate.

## Lifecycle

| Command | From desired state | Desired state after | Outbox event |
| --- | --- | --- | --- |
| `validate` | any | unchanged | none (Odoo-local snapshot) |
| `provision` | absent, unknown, disabled | provisioned_disabled | `campaign.provision.requested.v1` |
| `synthetic_test` | provisioned_disabled | synthetic_tested | `campaign.synthetic_test.requested.v1` |
| `activate` | synthetic_tested, disabled | active | `campaign.activate.requested.v1` |
| `disable` | active, synthetic_tested | disabled | `campaign.disable.requested.v1` |
| `reconcile` | any | unchanged | `campaign.reconcile.requested.v1` |
| `rollback` | any | unchanged | new immutable configuration version + `campaign.reconcile.requested.v1` |

State-changing commands require `control_status = validated`. Every command
locks the campaign row, compares `expected_configuration_version` with the
current version (`0` before the first validation; version-zero validation
creates version `1`) and returns `409 CONFIGURATION_VERSION_CONFLICT` on
mismatch. Commands are idempotent on the caller `Idempotency-Key`: a retry
returns the original run and its `command_id` (the outbox `event_uuid`,
`uuid5(workspace_uuid, key)`).

Delivery is pull-only. Middleware claims the event through
`/api/v1/integration/outbox/claims` and acknowledges durable intake; the
acknowledgement sets the run's `delivery_state = accepted` and
`delivery_acknowledged_at` and nothing else. A dead-letter before intake
fails the run and blocks control status. Only the read-back moves
`effective_state`:

* observed state equals the run's requested state: run `succeeded`,
  `effective_state` advanced, outcome `COMPLETED`;
* observed state equals the previous effective state: execution lag,
  outcome `IN_PROGRESS`, nothing changes;
* a `reconcile` observing a divergence: run `succeeded`, `effective_state`
  updated, `control_status = blocked` (`PROVIDER_STATE_DRIFT`), outcome `DRIFT`;
* any other terminal state: run `failed`, `effective_state` updated,
  `control_status = blocked`, outcome `BLOCKED`;
* stale or future `configuration_version` (or a foreign `manifest_hash`):
  `409 STALE_CONFIGURATION_VERSION`, no mutation;
* same `Idempotency-Key` with the same body: the original receipt; with a
  different body: `409 IDEMPOTENCY_CONFLICT`.

The read-back request carries the 16 contract fields (no
`execution_status`); the `Idempotency-Key` header must equal the body's
`idempotency_key`. The response is `status: APPLIED`, `readback_id`, and the
bound echoes `event_uuid`, `command_id`, `configuration_version`,
`effective_state`, `correlation_id`.

## Creation

`POST /platform/v1/campaigns` accepts an explicit allowlisted schema and
resolves the business unit by public code or UUID; lifecycle state, ownership,
agents, active flags and internal identifiers are never caller-set. Created
campaigns have `design_automation_enabled = false` and are configured through
this lifecycle.

The workspace endpoint is a calculated projection over canonical campaign,
membership, profile, and agent-channel models.
